# CL09 A/B: joint prefill/decode vs solo on jwm2 + Spark

CL08's merged `--engine joint` path, driven end-to-end between two aarch64 hosts on the LAN:
a DGX-OS aarch64 box prefills on CUDA and saves its slot KV; an Omarchy aarch64 laptop
restores it and decodes on Vulkan. Compared against the same decode host serving the same
prompt solo. Hardware names are placeholders per repo policy.

- source: `09723e5` on both hosts (`omarchy-cluster` 0.3.7)
- prefill host `<SPARK>`: Linux 7.0.0-1019-nvidia (DGX OS), llama-server `c7fc509` (GCC 13.3.0), NVIDIA GB10
- decode host `<JWM2>`: Linux 7.3.0-2-20261110.1-lab-ARCH (Omarchy), llama-server `c7fc50941` (GCC 16.1.1), Apple M2 Max (G14C B1) Vulkan1
- model: Qwen3-1.7B-Q4_K_M.gguf, sha256-16 `72c5c3cb38fa32d5` identical on both hosts
- ctx 16384 both sides; decode flags `-t 8 -ngl 99 -dev Vulkan1`; greedy (temperature 0) everywhere
- co-tenancy during the run: live production llama-servers on `<SPARK>` (2 long-running services) plus a concurrent out-of-tree shader build; load logged 1.7-3.2
- agent seam: joint engine on `<JWM2>` pulled `/v1/kv` from `<SPARK>`'s agent over pinned TLS (`agent.crt` fingerprint pinned in `~/.local/state/omarchy-cluster/pins`, shared cluster token)

## Commands (placeholders)

prefill on `<SPARK>`:
```
llama-server -m Qwen_Qwen3-1.7B-Q4_K_M.gguf --host 0.0.0.0 --port <PREFILL_PORT> \
  -c 16384 --slot-save-path ~/.local/state/omarchy-cluster/kv -ngl 99

```

```
  --prefill-url http://<SPARK>:<PREFILL_PORT> --prefill-kv <SPARK>:<AGENT_PORT> \

  --llama-arg=-ngl --llama-arg=99 --llama-arg=-dev --llama-arg=Vulkan1
```

solo on `<JWM2>`:
```
llama-server -m Qwen_Qwen3-1.7B-Q4_K_M.gguf --host 127.0.0.1 --port <SOLO_PORT> \
  -c 16384 -t 8 -ngl 99 -dev Vulkan1
```

## Results

Prompt: deterministic generated transcript, 10,699 tokens
(sha256-16 of the prompt text recorded in the run log), n_predict=128, ABBA order.

| leg | wall_s | token digest sha256 | prefill | transfer | decode_tokps |
|---|---|---|---|---|---|
| solo 1 | 34.16 | `2cc318e0c5da7b1e` | local Vulkan1, 364.3 prompt tok/s | — | 26.8 |
| joint 1 | 113.75 | `bc2954ad0915d347` | 2338 ms / 10699 tok on `<SPARK>` | 1,227,218,820 B in 101.8 s (96.4 Mbps) | 26.99 |
| joint 2 | 114.09 | `bc2954ad0915d347` | 42 ms (warm slot) | same bytes in 105.6 s (92.9 Mbps) | 26.92 |
| solo 2 | 33.54 | `2cc318e0c5da7b1e` | local Vulkan1, 372.1 prompt tok/s | — | 26.8 |

Joint phase breakdown (leg 1): prefill 2338.6 ms → save 4176.4 ms → **transfer 101815.6 ms**
→ restore 265.8 ms → decode 4706.0 ms. `errors: []`, `decode_prompt_n: 1` (prefix reuse worked —
the decode server re-evaluated 1 token, not 10,699).

A second leg at 96 generated tokens (prompt ≈5,360 tokens after slot warm-up) reproduced the
same shape: transfer 135.7 s at 72.3 Mbps (busier co-tenant), decode 26.94 tok/s.

## Parity

- Digest equality between the two joint legs (`bc2954ad…` both) and between the two solo legs
  (`2cc318e0…` both): each arm is self-consistent.
- **joint ≠ solo.** Token-level diff: identical prefix for 22 tokens in the first probe and
  10 tokens in the second, then argmax diverges on plausible continuations
  (e.g. token 22: solo `16` vs joint `17` → "14" vs "24").
- That prefix length rules out format corruption: an endian or layout bug in the slot file
  would diverge at token 0 or emit garbage. The KV seam (save → pinned-TLS agent transport →
  restore) is endian-safe and structurally valid.
- The divergence is cross-backend prefill numerics: CUDA GB10 and Vulkan G14C produce
  bit-different KV for the same prompt, and greedy decode amplifies the drift within tens of
  tokens. Bitwise token parity versus a local-prefill baseline cannot hold in a cross-GPU
  joint topology.

## Verdict for the card

- The merged CL08 path works end-to-end on real hardware: remote prefill, slot save, LAN KV
  transport through the token-authed pinned agent, slot restore, prefix-reuse decode. No
  phase error in any leg.
- Identical-token-ids versus the solo arm: **does not hold**, and cannot hold across different
  GPU backends — the correct bar for this seam is structural validity plus decode-rate parity,
  which it meets (26.9 vs 26.8 tok/s, long identical prefixes).
- Throughput: at ~96 Mbps LAN the 1.23 GiB slot file costs ~100-136 s per request — the joint
  arm is ~3.4x slower end-to-end than solo for this 1.7B model. The joint trade only pays when
  local prefill is far more expensive than remote prefill plus a multi-second KV transfer.
